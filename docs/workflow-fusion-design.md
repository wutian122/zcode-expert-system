# ZCode 专家体系 · 融合设计基线

> 版本：v3.2.6 ｜ 融合基线日期：2026-11-16 ｜ 宿主适配更新：2026-11-26
> 适用范围：ZCode / Claude Code / Qoder Desktop。安装目录、命令命名与子代理派发名由宿主适配层处理；
> 本文只描述三平台共用的两轴路由、九阶段门禁与证据体系。
> 本文是九阶段工作流与门禁体系的**书面依据**（`SKILL.md` 与 `config/workflow.json` 引用它）。
>
> **权威顺序**：`config/workflow.json`（机器可读声明）> 本文（设计意图与取舍理由）> `SKILL.md`（操作说明）。
> 三者冲突时以 `workflow.json` 为准；本文解释「为什么这样设计」，不重复声明具体字段值。

## 一、这套体系要解决什么

三个来源各有一块短板，融合是为了补上彼此的缺口：

| 来源 | 强项 | 短板 |
|---|---|---|
| **OpenSpec** | 规格真相源：proposal / design / tasks / delta spec 四件产物，delta 可机械合并；已内置为 `scripts/openspec_engine.py`（8 个子命令：list / new-change / status / instructions / validate / sync-specs / archive-change / validate-specs），纯 Python 标准库，无需外部 OpenSpec CLI | 只管「规格写没写」，不管「实施有没有按规格做」 |
| **Superpowers** | 执行纪律：TDD、根因调查、审查派发、验证门函数；已收编为 `zes-*` 技能（vendor/skills/zes-*） | 纪律靠自觉执行，没有机械核验 |
| **多 Agent** | 领域能力：331 位专家按域派发 | 派发后缺少状态与证据的追踪 |

融合的判断是：**把 Superpowers 的纪律变成 OpenSpec 的产物，再用一个机械核对脚本盯住产物。**

于是有了两轴：

- **域轴**（`zcode_expert_system.py`）：这活该派谁 —— 32 类 → 331 专家
- **规模轴**（`zcode_dev_workflow.py`）：这活要走多长流程 —— 只读/轻量/中/大/Bug

两轴正交：规模决定阶段裁剪，域决定 `subagent_type`。

## 二、九阶段与门禁的拆分依据

原始规范的门禁编号 G0–G8 与九阶段**不是一一对应**的，直接照搬会产生两处含混：

1. **S6 同时吃 G6（审查门禁）和 G7（验证门禁）**。审查通过 ≠ 验证通过：
   审查看「代码与规格是否一致」，验证看「所需验证是否本会话真跑过」。
   合成一个门会让「reviewer 说 OK」替代「测试真绿」。
   → 保留 `G6+G7` 复合门禁，`workflow_check` 分两条独立判据。

2. **S7（交付）与 S8（归档）原本共用 G8**。但两者失败后果不同：
   - 交付失败 → 代码没合进去，重做即可
   - 归档失败 → `openspec/` 目录已搬迁、主 spec 已被覆盖，回滚代价高
   → 拆为 **G8a（交付后重测）/ G8b（同步归档）**，S8 独立设 `stop_for_owner`。

停机点（`stop_for_owner`）的取舍标准是**「错一次的代价」**：

| 阶段 | 停机 | 理由 |
|---|---|---|
| S1 | ✅ | 设计错了，后面全白做 |
| S2 | ✅ | 规格错了，门禁盯的是一个错东西 |
| S4 | 基线红时 | 不阻断开工，但必须老板表态是否带病 |
| S7 | ✅ | 集成方式（合并/PR/保留）是老板的决定 |
| S8 | ✅ | 不可逆：目录搬迁 + 主 spec 覆盖 |

## 三、裁剪矩阵的语义（必 / 简 / 条 / -）

`config/workflow.json` 的 `trim_matrix` 用四个标记控制每阶段在每规模下做多少：

| 标记 | 含义 | 检查器行为 |
|---|---|---|
| `必` | 完整执行 | 全部检查项执行，原定严重度 |
| `简` | 必做但简化 | 只执行**机器承重项**；其余项不 emit（不是跳过） |
| `条` | 条件触发 | 先判触发条件：成立按「必」，不成立 emit 一条带理由的 SKIP |
| `-` | 该规模不适用 | 检查器不执行，发一条 `inapplicable:trim` SKIP |

**「简」的判据只有一条：这项是下游机械消费的输入，还是给人看的格式？**

- 下游消费 → 简也必须查：计划文件存在（`task-brief` 要读）、`### Task N:`
  （`task-brief` 按它解析）、勾选框（`openspec list --json` 的 totalTasks 来源）、
  `independence`（唯一硬性交付禁止项）
- 纯格式/给人看 → 简可省：8 个必备段的存在性（查 `^## Architecture` 只能证明
  有人写了标题，证明不了内容成立）

**两条不可越的边界**：

- 「简」只减项，**不减严重度**。绝不能把 FAIL 降成 WARN —— 那是门禁形同虚设。
- 「简」不减到零。每阶段的机器承重项固定，不因规模而消失。

**「条」当前等价于必（P8 裁决记录，2026-11-17）**：

`trim_matrix.light` 曾对 S4/S7 标「条」，但实现里除 S2/S8 外没有任何触发引擎，
`check_*` 对「条」一律按「必」执行。裁决**不改代码实现，改配置与文档说真话**：

- `workflow.json`：light 的 S4/S7 已改为「必」，S2/S8 保留「条」——它们有真触发实现
  （`inapplicable:trigger:openspec` / `inapplicable:no_change`，触发条件是**项目属性**
  而非调用方参数）。
- 不实现通用 `apply_when` 触发引擎的理由：「条」的触发判据只能是「调用方给没给
  `--plan`」，等于「我不传参数 ⇒ 门禁不查我」，与 readonly 后门同构。
  主控实证：light + 任务全完成 + 无 `--plan` 恰好 3 条 FAIL 全部是
  `unverifiable:plan_required`；实现「条」让它们 SKIP 后 rc=0，
  而基线与集成重测从未被验证——那是新假绿。
- 佐证：`LIGHT_KEEP["S3"]` 把 `plan_exists` 列为机器承重项，说明原作者意图就是
  「light 必须有（简化）计划」，`S3="条"` 是写错的标记而非未实现的功能。
- 口径三方一致：`workflow.json`（条/必按上）、`SKILL.md` 轻量行、本文档本节。

## 四、状态机：七态是状态，SDD 四态是边标签

`PENDING → IN_PROGRESS → REVIEW → NEEDS_FIX → DONE`，加 `BLOCKED`、`PARKED`。

SDD 的四态（DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED）**不是状态**，
它们进入状态机后立即转化为状态转移：

| SDD 报告 | 转移 |
|---|---|
| DONE / DONE_WITH_CONCERNS | `IN_PROGRESS → REVIEW` |
| NEEDS_CONTEXT | `IN_PROGRESS → IN_PROGRESS`（自环） |
| BLOCKED | `IN_PROGRESS → BLOCKED` |

为什么必须分开：状态机的每个状态对应一条**可机械判定的证据要求**
（如 `DONE` 当且仅当 tasks.md 为 `- [x]`），而 SDD 的四态是子代理的**自述**。
自述不能直接当状态——那等于让实施者自己宣布通过。

## 五、证据分级：为什么 P4 必须导出才能删

| 级 | 位置 | 内容 | 生命周期 |
|---|---|---|---|
| P1 | git commit 或文件快照 sha256 | 实际改了什么 | 交付后归档 |
| P2 | `openspec/changes/<n>/tasks.md` + 计划文档 `## Rulings` | 完成度、ADR 决策 | 归档永久 |
| P3 | 计划文档的 `## Baseline` / `## Review` / `## Rulings` / `## Integration Verification` | 基线、审查、裁决、交付重测 | 随仓库 |
| P4 | `.superpowers/sdd/<plan>/` | ledger / brief / report / 快照 | 终审后删 |

**铁律：P4 未导出，禁止删 workspace。**

理由是这条链会让两类最关键的信息整体消失，而它们恰好最不容易被察觉缺失：

1. **基线**：没有基线，「这次改动有没有引入新的红」就无法回答
2. **裁决**：`Rulings` 记录的是「老板不知道的那些决定」——删了没人记得为什么这样做

所以 `workflow_check` 把「计划文档有没有 `## Baseline`」和「有没有 `## Rulings`」
当作 FAIL/WARN 判定项，而不是只检查 workspace 里有没有 ledger。

## 六、无 git 的并行模型（老板决策）

本体系**不使用 Git Worktree**。这不是保守，是守恒：

| 保留的并行 | 取消的并行 |
|---|---|
| 只读调查并行（多个无关失败分域取证） | **多 Agent 实施并行** |
| 审查并行（多位 Reviewer 同批任务，只读无冲突） | — |

**原因**：没有隔离工作区就不能有两个写者。同一目录两个写者 = 后写覆盖先写，
且无法审计谁改了什么。

git 降为可选增强层：

| 探测 | 变更集来源 | 审查独立性 | 收尾 |
|---|---|---|---|
| 有 git | `review-package` 的 `BASE..HEAD` diff | L0（原始 diff 可独立审） | finishing 三选一 |
| 无 git（默认） | 文件快照 sha256 差集 + 变更文件全文 | **L1**（快照由主控自算，非原始 diff） | 改动清单验收 |

**变更集由主控独立计算，不由实施者自述** —— 这是无 git 环境下仍可信的唯一依据。
「无 git 就自动降为 L1」这一条由 `_pick_reviewer(has_git=...)` 实现在派发计划里，
写进账本，交付时显式声明。

## 七、冲突消解：十条裁决的来由

在两套体系交叉处，以下十处会产生真实冲突。裁决规则记在
`config/workflow.json` 的 `conflict_rulings`，此处说明最难的四条：

**W1 无 worktree 即无实施并行** —— 见第六节。

**W4 基线红不阻断开工，但必须记清单**。
若「基线红就停工」，等于要求先修完所有历史遗留才能动新活；
若「基线红不管」，则无法区分「本次引入」与「本来就有」。
折中是：记清单 → 此后每个红项比对清单内外 → 交付报告列出全部既存红项。

**W8 PARKED 默认禁归档，「接受不修」必须迁出到新 change**。
PARKED 是「已知问题但本轮不修」。若允许带 PARKED 归档，它就变成了
「悄悄消失的问题」——归档后的变更没人会再翻。
所以归档门禁遇到 PARKED 直接 FAIL，要把该问题迁到新 change 里留档。

**W10 两轴强制串行** —— 所有任务（含只读与机械任务）先规模后域，
域路由不得跳过；豁免仅两级：闲聊/问候、老板明示且记 Ruling。
readonly 派 **analyst**（领域专家只读分析，四段式输出），不进实施流程；
执法锚：`workflow_check` 的 S0.DOMAIN 检查项（A 案，按账本 Triage 域路由两行判定）。

## 八、被推翻或收窄的设计（留档以免重犯）

这些是设计过程中被否掉的方案，记下来是为了避免后人再走一遍：

| 曾考虑 | 否决理由 |
|---|---|
| 用 `PreToolUse` 钩子拦截主控直接改码 | 钩子看不到调用者身份（主控与子代理是同一类执行体），三宿主 hook 能力也不一致——同一门禁要写三份，缺一份就静默放行。**改为**：落盘派发证据 + `workflow_check` 事后机械核对（见第十节） |
| 用外部 LLM/Embedding 做语义精判 | 插件运行在会话内，会话里的模型就是可用模型。再接外部 LLM 既重复又要凭据要花钱。**改为**：Python 只做词元粗筛并显式标注 `selection_basis=heuristic`，语义判断交主控 |
| 把 30+ 条检查项文案外部化进 JSON（i18n 思路） | 会让现有按中文字面断言的测试全部失效，可读 diff 变成键值查找，收益仅为「文案可改」——本项目没有多语言需求 |
| `decisions.md` 作为独立 ADR 账本 | 与计划文档 `## Rulings` 职责重叠，且后者已有产出方与机械校验。**改为**：收回对 `decisions.md` 的引用，统一指向 `## Rulings` |
| 把「唯一声明源」做成全量字面量动态化 | 阶段 ID 本身是配置主键，消费者必须写 `"S5"` 才能查表——这是**使用**不是硬编码。真正该防的是**派生事实被复制**（阶段中文名、必备段清单、32 领域名），这四项用契约测试钉死即可 |
| 用中文分词 / LLM 替换 Bug 分诊词表 | 分词需引入三方库（违反零依赖），LLM 需外部服务（见上）。**维持**词表 + 双向守卫 + `reasons` 可追溯 |
| 用人工 Markdown 检查表做验收 | 会被跳过。**必须机械可验** —— 这是整个 `workflow_check.py` 存在的唯一理由 |

## 九、「不靠自觉」的落地形态

一句「要按流程做」写在文档里，等于没有。所以每个纪律都配一个机械判据：

| 纪律 | 机械判据 |
|---|---|
| 不许假绿 | SKIP 只剩一个合法含义「按声明不该查」（理由码 `inapplicable:`），其余一律 FAIL |
| 不许静默 | 未裁剪阶段至少产出一条检查项（INV-R1），靠 `run()` 兜底而不依赖各检查器自觉 |
| 不许拿「查不了」当放过 | 查不了 = FAIL，WARN 只表达「此刻不必成立」（INV-R3） |
| 不许主控自兼实施者 | 完成态任务必须有 implementer 派发行，且 `agent` 是注册表专家（S5.DISPATCH_IMPLEMENTER） |
| 不许主控自兼审查者 | `independence: L0` 必须有 reviewer 派发行，且与实施者非同一席专家（S6.REVIEWER_DIFFERENT_EXPERT） |
| 不许 L2 交付 | `independence` 取**最坏值**（只能造成假红，不能造成假绿） |
| 不许删证据 | P4 未导出禁止删 workspace；删账本本身判 FAIL（见第十节） |
| 不许靠人记得 | 每个检查项有稳定 id；改了配置没同步代码，`--self-check` 当场报 drift |

**最后一条尤其重要**：`workflow_check.py` 自己是验证工具，它坏了无法自证。
所以它额外提供 `--self-check`（配置 ↔ 代码一致性，rc=2）与 `--explain`
（解析明细，让用户 30 秒自查是格式问题还是工具问题）。

## 十、派发证据门禁：为什么不是 PreToolUse

**问题**：账本 `## Dispatches` 与计划 `## Review` 的 implementer / reviewer
字段早就写在模板里，但早期 `workflow_check.py` 从不解析它们。后果是
「主控在自己会话里改码、又自己审查」，只要在账本写一句 `independence: L0`
就能拿完成态通过——证据链上没有一处机械拦截。

**约束（本设计的硬边界）**：

1. **主控不能兼实施者**。完成态任务必须有对应的 implementer 派发行，
   且该行的 `agent` 必须是注册表内的专家。没有派发行 = 没有实施者，
   「主控自己改码」不构成完成。
2. **主控不能兼审查者**。`independence: L0` 必须有 reviewer 派发行；
   reviewer 与 implementer 不得是**同一位注册表专家**（按注册表身份判定，
   自述 `category` 改不动事实——否则改个分类就能把自审说成异域审查）。
3. **主控是唯一状态写者**，但它写的是「谁做了什么」的记录，不是自我评价。
   审查结论由异域专家给，主控只负责核验与落账。

**为什么不在 `PreToolUse` 上拦？** 这是本文最需要留档的一次否决：

| 方案 | 否决理由 |
|---|---|
| `PreToolUse` 钩子拦截写盘工具 | 钩子只看得到「某个工具调用」，看不到**调用者身份**。子代理与主控在宿主里是同一种执行体，钩子无法区分「主控自己写」与「implementer 子代理写」——拦截只能变成「一律禁止写盘」 |
| 同上，改为按会话/进程区分 | 三宿主能力不一致：Qoder 只落 `UserPromptSubmit` 一个 Hook，Claude Code / ZCode 的钩子 schema 也各不相同。同一门禁要写三份宿主实现，且任何一份缺失就静默放行（假绿） |
| 同上，改为阻断工具调用 | 阻断发生在**实施中途**，此时半成品已落盘；而证据门禁要回答的是「完成态是否可信」，属事后判定。中途阻断既救不回已写的内容，又会误伤只读调查 |
| **落盘证据 + 事后机械核对（采用）** | 证据在产物里（账本派发行、brief、report、计划身份行），宿主无关、可离线复核、可 `--self-check` 自证。缺证据 = FAIL，而不是「拦不住就算了」 |

**七项检查**（`scripts/workflow_check.py`，`tests/test_dispatch_evidence.py` 覆盖）：

| 检查 id | 抓的破坏 |
|---|---|
| `S5.DISPATCH_IMPLEMENTER` | 完成的任务没有 implementer 派发行；派发行缺必需字段 |
| `S5.DISPATCH_ORPHAN_REPORT` | 有 report 却没有对应派发行（来源不明）；派发行的 report 指向别的任务 |
| `S5.IMPLEMENTER_IS_EXPERT` | 实施者不是注册表专家（含主控自称） |
| `S6.REVIEWER_DISPATCH` | 声明 L0 却没有任何 reviewer 派发行 |
| `S6.REVIEWER_DIFFERENT_EXPERT` | reviewer 与 implementer 是同一席专家；reviewer 不在注册表内 |
| `S6.L0_REQUIRES_DISPATCH` | 声称 L0 独立审查，但账本无独立审查证据 |
| `S6.REVIEW_IDENTITIES` | 计划 `## Review` 的身份行与账本派发行不一致（张冠李戴） |

**两条附带的取舍**：

- **删账本不算清理**。workspace 在、brief/report 在、`progress.md` 被删 →
  直接 FAIL（`missing:ledger`）。否则「删掉记录」就是最省事的过门方式。
- **适用面只对完成集执法**。workspace 整删（交付后按铁律清理）、未开工、
  无账本 → `inapplicable:` SKIP。门禁不能靠「查不了」放过，也不该把
  「还没开始」判成缺陷。

## 十一、已知边界

诚实记录这套体系**做不到**什么：

- **语义质量不可机械判定**。审查是否到位、根因是否真到位，脚本答不了。
  它只保证「该有的产物在、该跑的验证跑了」。
- **词表驱动的分诊有精度上限**。`zcode_dev_workflow.py` 的 Bug 判定靠词表，
  双向误判无法根治，只能靠双向守卫 + `reasons` 保留依据 + 允许人工覆盖。
- **`--scale` 是调用方自报**。脚本无法验证「这真的是一次只读任务」。
  缓解靠两条交叉校验：`readonly` 同时给了 change/plan → WARN；
  账本记录的规模与 `--scale` 冲突 → FAIL。
- **子代理自述不可信**。所有「实施者说完成了」都必须由主控用变更集与
  命令输出独立核验；这是 `verification-before-completion` 门函数存在的原因。
- **OpenSpec CLI 内置后，仍无法自动验证产物语义正确性**。脚本只能检查四件
  产物文件是否存在、结构是否规范；需求描述是否准确、是否真正解决用户
  问题，仍需老板审阅与主控人工判断。

# Bug 修复模板（根因优先）

> 铁律：**无根因不修复；无失败测试不修码；无证据不下结论。**
>
> **P3 落盘（强制）**：本报告的入口分诊、9 问根因、假设三段、分级方案、
> 副作用自查、双确认、RED、red-green 四段复验、全量回归，必须同步到计划文档
> `## Bug Investigation` 段。会话记录与 P4 workspace 都不是 P3，终审后会删除。
> 没有计划文档时，先建一个最小计划，再落这一段。

## 1. 入口分诊（7 类）

| 类型 | 判定 | 增用手段 |
|---|---|---|
| 代码逻辑 Bug | 行为错误、报错指向项目代码 | 全流程 |
| 构建/CI/脚本失败 | 编译、lint、打包、流水线红 | **全量读日志**，定位首个 error |
| 依赖/环境 Bug | 升级后出现、他机正常 | 查上游 issue + changelog（**附 URL**） |
| Web 前端/UI Bug | 渲染、交互、样式 | 内置浏览器复现 + 截图取证 |
| 远程/服务器问题 | 仅 VM 复现 | remote-shell（先征询老板） |
| 工具自身失灵 | 技能不触发、hook 不跑 | 走对应诊断技能 |
| 性能问题 | 慢、内存涨 | 先计时/剖析拿数据，**禁止无数据猜测** |

**会话异常例外**：问题主体是 **agent 会话本身**（技能未触发、计划被忽略、重复派单、耗时异常）→ 走会话诊断（只报告），**不进根因流程**。

## 2. 根因调查（Phase 1，9 问必答）

1. 在什么条件下发生？
2. 能否稳定复现？
3. 预期行为是什么？
4. 实际行为是什么？
5. 哪个模块异常？
6. **直接原因**是什么？
7. **根本原因**是什么？
8. 是否存在相同类型的问题？
9. 修复后如何防止再次发生？

## 3. 假设三段

```
假设：<X 是根因>，因为 <Y>
预期证据：若为真应看到 <A>
最小检验：只改 <B> 观察 <A>
```

一次一个变量。证伪即回 Phase 1。

## 4. 分级 + 方案（≥2 套）

| 级别 | 含义 |
|---|---|
| 🔴 致命 | 数据损坏、安全漏洞、服务不可用 |
| 🟠 严重 | 核心功能失效 |
| 🟡 一般 | 局部异常、有绕过 |
| 🟢 优化 | 性能/可维护性 |

每套方案含：思路 / 改动范围 / 风险 / 工作量 / 测试策略。
唯一方案须声明「经客观分析仅 1 个可行方案，原因：…」。

## 5. 副作用自查（方案发出前完成）

- 下游消费者清单
- 行为反转清单
- 组合影响
- 阻断级风险无防护前不得请求确认

## 6. 双确认门禁

❶ 方案等老板选 A/B/C，**未选不改码**
❷ 选定后确认执行，动词白名单：执行/开始/动手/go/确认执行/修
　「好的/OK/行/修吧」**不视为确认**

**快速通道**：副作用自查已并入、无破坏性操作、分级 🟡/🟢 时，方案末尾写明「选 A/B/C 即视为批准执行」，选定后直接进 Phase 4。🔴/🟠 保留双门禁。

## 7. TDD 修复

先写**复现该 Bug 的失败测试**，看它失败，失败原因必须 = 缺陷本身（不是笔误）。

## 8. red-green 复验（不可省）

```
修复后通过（GREEN） → 还原修复 → 必须复红（RED） → 恢复修复 → 再绿
```

未走完此循环，不得声称"回归测试已写"。

## 9. 升级路径

同一问题 **3 次修复失败** → 停止，质疑架构（耦合/共享状态），与老板讨论后再动。

## 10. 复盘

1–3 句记录根因模式：触发条件 → 根因 → 通用预防。
